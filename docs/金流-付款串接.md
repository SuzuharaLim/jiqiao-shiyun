# 讓使用者可以付款：金流串接指南

> 你問：「要讓使用者可以付款，我們要怎麼做？」這份說明給你**完整可行的路線**：選金流商 →
> 開帳號拿金鑰 → 前後端怎麼接 → 在 Cloud Run + Cloud SQL 上怎麼放。程式已備好 scaffold
> （`/api/payments/intent`、`/api/payments/webhook`、訂單狀態機），你只要接上一家金流商即可上線。

---

## 一、先搞懂金流的「三段式」流程（各家都一樣）

```
① 前端要結帳
   → 呼叫我們的後端 POST /api/payments/intent（伺服器算金額、建「待付款」訂單）
② 後端跟「金流商」建立一筆交易
   → 拿到 clientSecret / prime 交易 / 付款頁 URL，回給前端
③ 使用者在金流商的安全介面輸入卡號付款（我們的伺服器「絕不」碰卡號）
   → 金流商付款成功後，打我們的 POST /api/payments/webhook
   → 後端驗章、把訂單改成「已付款」，寄出貨/開通
```

重點：**信用卡卡號永遠只進金流商的元件**（Stripe Elements、TapPay SDK、綠界/藍新的付款頁），
我們的後端只存「訂單」與「交易結果」，這樣才符合 PCI-DSS、也最安全。本專案的安全規則也要求
「不要把卡號輸入任何欄位」——用金流商的托管欄位正是正解。

---

## 二、選一家金流商（台灣情境建議）

| 金流商 | 適合 | 支援 | 開發體驗 | 撥款/費率(約) |
| --- | --- | --- | --- | --- |
| **Stripe** | 有跨境/訂閱、想要最好的 API 與測試環境 | 信用卡、Apple/Google Pay、訂閱 | ★★★★★ 文件最佳 | 2.9%+NT$10；台灣本地已可收 TWD |
| **TapPay** | 台灣主流、要接多家收單行、LINE Pay/街口 | 信用卡、LINE Pay、Apple/Google Pay、街口 | ★★★★ SDK 取 prime | 依合約 |
| **藍新 NewebPay** | 台灣中小商店最常見、幕後金流 | 信用卡、ATM、超商、LINE Pay | ★★★ 表單重導＋回傳驗章 | 依合約 |
| **綠界 ECPay** | 同上，超商代碼/物流整合強 | 信用卡、ATM、超商、物流 | ★★★ 表單重導 | 依合約 |
| **LINE Pay** | 客群重 LINE | LINE Pay | ★★★ | 依合約 |

**建議：先用 Stripe 把流程跑通（測試最快、文件最好），要正式對台灣客群收款再加 TapPay 或藍新。**
本專案 `PAY_PROVIDER` 環境變數即用來切換（`demo`/`stripe`/`tappay`/`newebpay`/`ecpay`/`linepay`）。

## 三、要準備的帳號與金鑰（不需寫進程式，放 Secret Manager）

以 **Stripe** 為例：
1. 到 stripe.com 註冊商家帳號、完成企業/負責人驗證（要能收款需通過審核）。
2. 取得 API 金鑰：`STRIPE_SECRET_KEY`（後端用，sk_...）、`STRIPE_PUBLISHABLE_KEY`（前端用，pk_...）。
3. 建立 Webhook 端點指向 `https://<你的-cloud-run-網址>/api/payments/webhook`，取得 `STRIPE_WEBHOOK_SECRET`（whsec_...）。
4. 測試卡號：`4242 4242 4242 4242`、任意未來到期日、任意 CVC。

> ⚠️ 金鑰請勿寫進程式或前端。用 Cloud Run 的 Secret（見第五節）。我（AI）也不會、也不應該替你輸入這些憑證——請你自己在各金流商後台與 GCP Secret Manager 設定。

## 四、程式怎麼接（本專案已備好接點）

### 已就緒的後端 scaffold（`server/index.js`）
- `POST /api/payments/intent`（需登入＋CSRF）：伺服器**重新計算金額**、建立**「待付款」訂單**，回傳 `{ provider, orderId, amount, currency, next }`。
- `POST /api/payments/webhook`：金流商付款完成後打這支，驗 `x-webhook-secret`（正式要改成驗 provider 簽章）後把訂單改「已付款」。
- 訂單狀態：`處理中 / 待付款 / 已付款 / 付款失敗`，存 Cloud SQL `orders` 表。
- 前端 `src/api.js` 已有 `api.payIntent(...)`。

### 接 Stripe 的最小改動（示意）
後端 `intent` 內，把 `demo` 分支換成建立 PaymentIntent：
```js
// npm i stripe；env: STRIPE_SECRET_KEY
import Stripe from 'stripe'
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY)
const pi = await stripe.paymentIntents.create({
  amount: total * 1,            // TWD 為零位小數幣別：金額即元（不用 ×100）
  currency: 'twd',
  metadata: { orderId: id, userId: req.user.id },
})
res.json({ provider: 'stripe', orderId: id, amount: total, clientSecret: pi.client_secret })
```
前端結帳頁用 Stripe.js + Elements（金流商托管的卡號欄位）以 `clientSecret` 完成付款；
Webhook 收 `payment_intent.succeeded` → 依 `metadata.orderId` 更新訂單。**驗章**：
```js
const event = stripe.webhooks.constructEvent(rawBody, req.headers['stripe-signature'], process.env.STRIPE_WEBHOOK_SECRET)
```
（webhook 要用 raw body，需為該路由關掉 express.json，改 express.raw。）

### 接 TapPay（台灣、取 prime）流程
前端載入 TapPay SDK → 使用者輸入卡號在 TapPay 的 iframe 欄位 → 取得 `prime` → `POST /api/payments/confirm { prime, orderId }` → 後端用 `PARTNER_KEY` 呼叫 TapPay Pay-by-Prime → 成功更新訂單。

### 接 藍新/綠界（表單重導）流程
後端 `intent` 產生**加密表單參數**（用商店 `HashKey/HashIV` 簽章）→ 回 `paymentUrl + formFields` → 前端自動 submit 重導到金流頁 → 使用者付款 → 金流商 `ReturnURL/NotifyURL` 打我們 webhook（**驗 `CheckMacValue`/`TradeSha`**）→ 更新訂單。

## 五、在 Cloud Run + Cloud SQL 上放金鑰與 Webhook

沿用 `docs/部署-CloudRun-PostgreSQL.md`，多做三件事（都在 Cloud Shell）：

```bash
# 1) 金鑰進 Secret Manager
printf "%s" "sk_test_xxx"   | gcloud secrets create stripe-secret     --data-file=-
printf "%s" "whsec_xxx"     | gcloud secrets create stripe-webhook-sec --data-file=-

# 2) 部署時掛進 Cloud Run（環境變數 + 密碼）
gcloud run services update jiqiao --region=asia-east1 \
  --update-env-vars="PAY_PROVIDER=stripe" \
  --set-secrets="STRIPE_SECRET_KEY=stripe-secret:latest,STRIPE_WEBHOOK_SECRET=stripe-webhook-sec:latest"

# 3) 到 Stripe 後台把 Webhook 指向：
#    https://<你的 cloud run 網址>/api/payments/webhook
```
訂單與付款狀態都存在 Cloud SQL（已持久化、多實例共享），對帳/客服可查。

## 六、上線前檢查清單

- [ ] 用測試金鑰（test mode）跑完整流程：下單 → 付款 → webhook → 訂單變「已付款」→ 收確認信。

- [ ] 金額一律**由後端計算**（本專案已如此），前端傳來的價格只當參考、不可信。
- [ ] 金鑰只放 Secret Manager，不進 repo、不進前端 bundle。
- [ ] 退款/發票流程（可先人工，之後接 provider 退款 API 與電子發票）。
- [ ] 切到正式金鑰（live）、完成金流商的商家審核與費率合約。
