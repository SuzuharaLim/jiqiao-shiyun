# 機巧時運 — 後端安全設計規格（可直接實作）

> 目標：把現有 Vite + React 純前端 SPA 的 localStorage 模擬登入，換成 **Node.js + Express + SQLite(better-sqlite3)** 的伺服器端 Session 認證，單一容器部署到 **Cloud Run**。本文件精確到「工程師直接照做」。
>
> **前提與已知限制（務必在程式與文件標明）：**
> - Cloud Run 容器檔案系統為**暫存**，SQLite 檔在重佈署／擴充（多實例）時會**重置且不共享**。正式環境須改用 **Cloud SQL / Postgres**（本規格所有 SQL 皆為標準語法，遷移成本低）。
> - **無真實 SMTP**：Email 驗證與重設密碼**流程完整實作**，但寄信改用 dev transport（連結寫入 log／非正式環境回傳）。正式須接 **SendGrid / SES**。
> - **無 OAuth 金鑰**：前端三顆社群按鈕（Google/LINE/Apple）維持 Demo，後端預留 `/api/oauth/*` 但本期不實作。
> - HTTPS 由 Cloud Run 提供，`Secure` cookie 因此在正式環境成立；本機測試需特別處理（見 §3.2）。

```jsonc

{

  }

```

- **Session 機制**：不用 `express-session` 套件，改**自建**「SQLite session store + HttpOnly cookie」，以便完全掌控「登入後換新 session id」「logout-all」「裝置清單」等需求。
- **CSRF**：自建**雙送 token（double-submit）**，不引入額外套件。
- **UUID**：Node 18+ 內建 `crypto.randomUUID()`，免額外套件。

## 1. SQLite Schema（CREATE TABLE，可直接執行）

檔案：`server/db/schema.sql`。以 `better-sqlite3` 於啟動時 `db.exec()` 套用。

```sql
-- 啟用外鍵、WAL（單機並發較佳）
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

-- ── users：帳號主體 ──────────────────────────────────────────
CREATE TABLE IF NOT EXISTS users (
  id                 TEXT    PRIMARY KEY,            -- UUID v4
  email              TEXT    NOT NULL,               -- 儲存正規化(小寫+trim)後的值
  email_normalized   TEXT    NOT NULL UNIQUE,        -- 唯一鍵：小寫、去空白，用來防重複註冊/列舉
  display_name       TEXT    NOT NULL DEFAULT '',    -- 對應前端 user.name
  handle             TEXT    NOT NULL DEFAULT '',    -- 對應前端 user.handle
  password_hash      TEXT    NOT NULL,               -- bcrypt hash（含 salt 與 cost）
  role               TEXT    NOT NULL DEFAULT 'user' -- 'user' | 'creator' | 'admin'
                             CHECK (role IN ('user','creator','admin')),
  email_verified_at  TEXT,                           -- ISO8601；NULL = 未驗證
  failed_login_count INTEGER NOT NULL DEFAULT 0,     -- 連續失敗次數（成功即歸零）
  locked_until       TEXT,                           -- ISO8601；> now 表示鎖定中
  created_at         TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  updated_at         TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
);
CREATE INDEX IF NOT EXISTS idx_users_email_norm ON users (email_normalized);

-- ── sessions：伺服器端 Session（cookie 只存不可猜的 session id）──
CREATE TABLE IF NOT EXISTS sessions (
  id            TEXT    PRIMARY KEY,                 -- 32-byte 隨機 base64url（放進 cookie 的值）
  user_id       TEXT    NOT NULL,
  csrf_token    TEXT    NOT NULL,                    -- 32-byte 隨機；double-submit 用
  expires_at    TEXT    NOT NULL,                    -- ISO8601 絕對過期
  ip            TEXT,                                -- 建立當下 IP（稽核/裝置清單）
  user_agent    TEXT,                                -- 建立當下 UA
  created_at    TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  last_seen_at  TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_sessions_user ON sessions (user_id);
CREATE INDEX IF NOT EXISTS idx_sessions_expires ON sessions (expires_at);

-- ── tokens：一次性用途 token（Email 驗證 / 重設密碼）──────────
-- 只存 token 的 hash，明碼只出現在寄出的連結，DB 外洩也無法直接使用
CREATE TABLE IF NOT EXISTS tokens (
  id          TEXT    PRIMARY KEY,                   -- UUID
  purpose     TEXT    NOT NULL                       -- 'email_verify' | 'password_reset'
                      CHECK (purpose IN ('email_verify','password_reset')),
  token_hash  TEXT    NOT NULL UNIQUE,               -- sha256(明碼 token)（hex）
  user_id     TEXT    NOT NULL,
  expires_at  TEXT    NOT NULL,                       -- ISO8601
  used_at     TEXT,                                   -- 已使用時間；NULL = 未使用
  created_at  TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_tokens_hash ON tokens (token_hash);
CREATE INDEX IF NOT EXISTS idx_tokens_user_purpose ON tokens (user_id, purpose);

-- ── audit_log：稽核軌跡 ─────────────────────────────────────
CREATE TABLE IF NOT EXISTS audit_log (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  event       TEXT    NOT NULL,                       -- e.g. 'login_success','login_fail','register',...
  user_id     TEXT,                                   -- 可為 NULL（未知帳號的失敗嘗試）
  ip          TEXT,
  ua          TEXT,
  detail      TEXT,                                   -- JSON 字串，額外脈絡（不得含明碼密碼/token）
  created_at  TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
  -- 不設 FK：即使 user 被刪，稽核仍應保留 → user_id 允許成孤兒
);
CREATE INDEX IF NOT EXISTS idx_audit_user ON audit_log (user_id);
CREATE INDEX IF NOT EXISTS idx_audit_event ON audit_log (event);
CREATE INDEX IF NOT EXISTS idx_audit_created ON audit_log (created_at);
```

**稽核事件列舉（`event` 允許值，字串常數化）：**
`register`、`register_duplicate`（同 email 重複註冊嘗試，統一對外訊息但內部記錄）、`email_verify_success`、`email_verify_fail`、`login_success`、`login_fail`、`login_locked`（帳號鎖定中仍嘗試）、`logout`、`logout_all`、`password_forgot_request`、`password_reset_success`、`password_reset_fail`、`session_expired`、`account_deleted`、`csrf_fail`、`rate_limited`。

## 2. 端點契約（Endpoint Contracts）

**通用約定：**
- 前綴 `/api`；`Content-Type: application/json`。
- 認證：需登入的端點讀 `sid` cookie → 查 `sessions` → 未過期 → 掛 `req.user`；否則 `401 { "error": "UNAUTHENTICATED" }`。
- **狀態改變端點（POST/DELETE）一律需 CSRF 檢核**（見 §3.4）。CSRF 失敗 → `403 { "error": "CSRF_INVALID" }`。
- 錯誤回應統一格式：`{ "error": "<代碼>", "message": "<繁中對使用者訊息>" }`。錯誤代碼機器可讀，message 給前端 toast。
- **防帳號列舉**：`/register`、`/login`、`/password/forgot` 對「帳號存在與否」一律回**相同訊息與相同狀態碼**，並做**回應時間常數化**（§3.7）。
- 所有時間戳 ISO8601 UTC。

`req.user` 對應前端形狀：`{ id, name: display_name, handle, email, role, email_verified: !!email_verified_at, guest: false }`。

### 2.1 `POST /api/register` — 註冊

| 項目 | 內容 |
|---|---|
| 輸入 | `{ email, password, displayName }` |
| 驗證 | `email`：zod email 格式、長度 ≤254、正規化為小寫+trim；`password`：長度 8–72（bcrypt 上限 72 byte）、至少含字母+數字；`displayName`：trim 後 1–40 字。 |
| 處理 | 1) 正規化 email；2) 查 `email_normalized` 是否存在。**存在或不存在都走相同耗時路徑**（見 §3.7），存在時**不建立**、記 `register_duplicate`、**仍回 201 同樣訊息**（防列舉）；3) 不存在則 `bcrypt.hash(password, 12)`、`INSERT users`（`role='user'`, `email_verified_at=NULL`）；4) 產生 `email_verify` token（明碼寄出、DB 存 hash，效期 24h）；5) dev transport 輸出驗證連結到 log。 |
| 輸出 | `201 { "ok": true, "message": "若此信箱可用，我們已寄出驗證信，請至信箱完成驗證。" }`。**不自動登入**（要求先驗證 Email）。 |
| 失敗 | 輸入不合法 `400 VALIDATION_ERROR`（欄位級錯誤放 `details`）；被 rate limit `429`（§3.5）。 |
| 稽核 | `register` 或 `register_duplicate`。 |

### 2.2 `POST /api/login` — 登入

| 項目 | 內容 |
|---|---|
| 輸入 | `{ email, password }` |
| 驗證 | zod 基本型別；正規化 email。 |
| 處理 | 1) 查 user（依 `email_normalized`）。**找不到時仍執行一次 dummy `bcrypt.compare`**（§3.7）避免時間差列舉；2) 若 `locked_until > now`：記 `login_locked`、回 §3.6 統一失敗訊息（`423` 或統一 `401`，見下註）；3) `bcrypt.compare`；**失敗** → `failed_login_count++`，達門檻設 `locked_until = now + 15min`、`failed_login_count` 歸零重算，記 `login_fail`，回統一 `401 INVALID_CREDENTIALS`；4) **成功但 `email_verified_at` 為 NULL** → 回 `403 EMAIL_NOT_VERIFIED`（可附「重寄驗證信」提示）；5) **成功且已驗證** → `failed_login_count=0`、`locked_until=NULL`；6) **建立新 session（新 session id）**、寫 `sessions`（含 csrf_token、ip、ua、expires_at）、Set-Cookie（§3.2）。 |
| 輸出 | `200 { "user": {...§2 形狀...}, "csrfToken": "<明碼>" }`。前端把 `csrfToken` 存記憶體，之後放進 `X-CSRF-Token` 標頭。 |
| 失敗 | 帳密錯 `401 INVALID_CREDENTIALS`（與「帳號不存在」**同訊息同碼**）；未驗證 `403 EMAIL_NOT_VERIFIED`；rate limit `429`；鎖定 `401`（對外訊息與一般失敗一致，避免洩漏鎖定狀態；內部稽核 `login_locked`）。 |
| 稽核 | `login_success` / `login_fail` / `login_locked`。 |

> 註：對外**不區分**「帳密錯 / 帳號不存在 / 帳號鎖定」——統一 `401` 與訊息「Email 或密碼不正確」。僅「Email 未驗證」例外回 `403`（此資訊本人已知，且需引導驗證）。若團隊要求連未驗證也不洩漏，可改為一律 `401` 並在 §2.7 提供重寄。

### 2.6 `POST /api/password/reset` — 執行重設密碼

| 項目 | 內容 |
|---|---|
| 輸入 | `{ token, newPassword }`（token 為明碼，來自連結） |
| 驗證 | `newPassword` 同註冊密碼規則；`token` 非空字串。 |
| 處理 | 1) `sha256(token)` → 查 `tokens WHERE token_hash=? AND purpose='password_reset'`；2) 檢核 `used_at IS NULL AND expires_at > now`，否則 `400 TOKEN_INVALID`；3) `bcrypt.hash(newPassword,12)` 更新 `users.password_hash`；4) 標記 token `used_at=now`；5) **撤銷該 user 全部 session**（`DELETE FROM sessions WHERE user_id=?`，強制重新登入）；6) 解除鎖定（`failed_login_count=0, locked_until=NULL`）。 |
| 輸出 | `200 { "ok": true, "message": "密碼已更新，請重新登入。" }`。 |
| 失敗 | token 失效/過期/已用 `400 TOKEN_INVALID`（統一訊息）；rate limit `429`。 |
| 稽核 | `password_reset_success` / `password_reset_fail`。 |

## 3. 安全細節（實作參數，逐項照做）

### 3.1 密碼雜湊（bcrypt）
- 演算法 **bcrypt，cost = 12**（Cloud Run 1 vCPU 下約 200–300ms，兼顧安全與 UX）。
- 明碼上限 **72 bytes**（bcrypt 特性）；驗證層先擋長度，超過拒絕而非截斷。
- **禁止**把密碼放進 log、audit detail、錯誤訊息、URL。
- 升級路徑：登入成功後若偵測 hash 的 cost 低於當前設定，可透明 re-hash（本期非必要）。

### 3.2 Session Cookie 屬性
```
Set-Cookie: sid=<32-byte base64url 隨機值>;
            HttpOnly;
            Secure;
            SameSite=Strict;
            Path=/;
            Max-Age=604800          // 7 天（同 sessions.expires_at）
```
- **`sid` 值**：`crypto.randomBytes(32).toString('base64url')`，只是查 DB 的 key，本身不含任何資料。
- **HttpOnly**：JS 讀不到，緩解 XSS 竊 cookie。
- **Secure**：只走 HTTPS。**本機測試**（http://localhost）Secure cookie 不會被瀏覽器保存 → 用環境變數 `COOKIE_SECURE`（正式 `true`、本機 `false`）控制；正式 Cloud Run 一律 `true`。
- **SameSite=Strict**：跨站請求不帶 cookie，強力緩解 CSRF（見 §3.4 為何仍加 double-submit）。
- **Path=/**：全站有效。
- **絕對過期**：`sessions.expires_at = now + 7d`。每次 `/api/me` 更新 `last_seen_at`；可選「滑動過期」但本期用固定絕對過期較安全簡單。
- **登入後換新 session id**：`/api/login` 成功**建立全新 session 列並發新 sid**；若請求本身帶了舊 sid，先刪舊列。杜絕 **session fixation**。

### 3.3 Session 生命週期與清理
- 每次讀 session：`expires_at <= now` 視為無效 → 刪列 + 回 401 + 記 `session_expired`。
- 定期清理：啟動時與每小時 `DELETE FROM sessions WHERE expires_at <= now`、`DELETE FROM tokens WHERE expires_at <= now OR used_at IS NOT NULL`（保留期依需求）。用 `setInterval`（單容器可行；正式多實例改排程）。

### 3.4 CSRF：雙送 token（double-submit）
即使 `SameSite=Strict` 已大幅緩解，仍加一層縱深防禦（避免瀏覽器相容性/未來放寬 SameSite/子網域風險）：
1. 登入時後端產生 `csrf_token`（32-byte 隨機）存 `sessions.csrf_token`，並在 `/api/login` 回應 body 回**明碼**（不是 cookie）。
2. 前端存記憶體，之後所有 **POST/PUT/DELETE** 請求帶標頭 `X-CSRF-Token: <明碼>`。
3. 後端中介：比對 `req.header('X-CSRF-Token') === sessions.csrf_token`（**常數時間比較** `crypto.timingSafeEqual`），不符 → `403 CSRF_INVALID` + 記 `csrf_fail`。
4. GET/HEAD/OPTIONS 免檢。
- `/api/login`、`/api/register`、`/api/password/forgot`、`/api/password/reset`、`/api/verify-email` 這些**尚未登入**的 POST，因無 session 可比對 CSRF，改靠 **SameSite=Strict + CORS 同源 + Origin 檢查**防護（見 §3.9）。

### 3.5 express-rate-limit 參數
以 IP（Cloud Run 需信任代理取真實 IP，見 §3.10）為 key：

| 端點 | windowMs | max | 逾限行為 |
|---|---|---|---|
| `POST /api/login` | 15 分鐘 | 10 次/IP | `429 TOO_MANY_REQUESTS`，記 `rate_limited` |
| `POST /api/register` | 60 分鐘 | 5 次/IP | `429` |
| `POST /api/password/forgot` | 60 分鐘 | 5 次/IP | `429` |
| `POST /api/verify-email/resend` | 60 分鐘 | 5 次/IP | `429` |
| 全站 `/api/*`（保底） | 1 分鐘 | 100 次/IP | `429` |

- `standardHeaders: true, legacyHeaders: false`；訊息統一「請稍後再試」。
- **雙層防護**：IP rate limit（擋分散嘗試）＋ §3.6 帳號鎖定（擋單帳號暴力）。

### 3.6 帳號鎖定
- 連續登入失敗 **5 次** → `locked_until = now + 15 分鐘`，`failed_login_count` 歸零。
- 鎖定期間任何登入（即使密碼正確）都回**統一失敗訊息**（不透露「已鎖定」），內部記 `login_locked`。
- 成功登入或成功重設密碼 → `failed_login_count=0, locked_until=NULL`。
- 參數用環境變數：`LOGIN_MAX_FAILS=5`、`LOGIN_LOCK_MINUTES=15`。

### 3.7 防帳號列舉 + 回應時間常數化
- **統一訊息 / 狀態碼**：register、login、forgot 對「存在/不存在」回相同結果（§2 已定義）。
- **時間常數化**：
  - login 找不到 user 時，**仍執行一次 `bcrypt.compare(password, DUMMY_HASH)`**（DUMMY_HASH 為啟動時預先 hash 好的固定假值），使有/無帳號的耗時相近。
  - register/forgot 中「不存在」分支補上等量工作或固定最小回應時間（例如包一層 `await sleep(baseline - elapsed)` 逼近固定 300ms），避免時間側信道。
- **不透露**：錯誤訊息、狀態碼、回應時間三者都不得區分帳號是否存在。

### 3.8 helmet 標頭
```js
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],                 // 若 Vite 產物有 inline，改用 nonce/hash，勿用 'unsafe-inline'
      styleSrc: ["'self'", "'unsafe-inline'"],// 視 styles.css 是否 inline 調整
      imgSrc: ["'self'", "data:", "https:"], // 允許外部圖（社群頭像等），可收緊
      connectSrc: ["'self'"],
      objectSrc: ["'none'"],
      frameAncestors: ["'none'"],            // = X-Frame-Options: DENY
      baseUri: ["'self'"],
      formAction: ["'self'"],
      upgradeInsecureRequests: []
    }
  },
  hsts: { maxAge: 31536000, includeSubDomains: true, preload: false }, // 1 年
  frameguard: { action: 'deny' },            // X-Frame-Options: DENY（防點擊劫持）
  noSniff: true,                             // X-Content-Type-Options: nosniff
  referrerPolicy: { policy: 'strict-origin-when-cross-origin' },
  crossOriginOpenerPolicy: { policy: 'same-origin' }
}))
```
- **HSTS**：Cloud Run 為 HTTPS，安全開啟。**本機 http 測試時**建議停用 HSTS（用 env 判斷），否則瀏覽器會強制 https 導致本機打不開。

### 3.9 CORS（同源）
- 全端**同源部署**（同一容器同時 serve `dist` 與 `/api`），前端呼叫 `/api/*` 為同源 → **理論上不需 CORS**。
- 仍加中介明確拒絕跨源：檢查 `Origin` 標頭；只允許 `self`（正式為 Cloud Run 網址 + 自訂網域，讀 env `ALLOWED_ORIGIN`）。跨源狀態改變請求直接 `403`。
- 對未登入 POST（login/register/forgot），加 **Origin 檢查**當 CSRF 補強。

### 3.10 輸入驗證 + 參數化查詢 + 代理信任
- **輸入驗證**：所有端點入口用 **zod schema** 驗型別/長度/格式；驗證失敗 `400 VALIDATION_ERROR`（附欄位級 `details`）。Email 一律正規化（`.trim().toLowerCase()`）。
- **參數化查詢**：better-sqlite3 一律用 prepared statement 佔位符 `?`，**禁止字串拼接 SQL**（防 SQLi）。例：`db.prepare('SELECT * FROM users WHERE email_normalized = ?').get(email)`。
- **輸出編碼防 XSS**：後端只回 JSON（不組 HTML）；前端 React 預設 escape。**禁用 `dangerouslySetInnerHTML`** 於任何使用者資料。
- **Cloud Run 真實 IP**：Cloud Run 在 `X-Forwarded-For` 帶原始 IP。設 `app.set('trust proxy', 1)`，讓 `req.ip` 與 rate-limit 取到真實 client IP（否則所有請求看似同一個代理 IP）。
- **回應體積/型別**：`express.json({ limit: '32kb' })` 限制 body 大小防 DoS。

### 3.11 密鑰與敏感值
- `SESSION_SECRET`（若之後改用簽章 cookie 需要）、`COOKIE_SECURE`、`ALLOWED_ORIGIN`、`APP_BASE_URL`（組驗證/重設連結用）、`DB_PATH` 全走**環境變數**，不進版控。
- token 明碼只出現在寄出的連結與（非正式環境）log；DB 只存 sha256 hash。
- `.env.example` 列出所有變數名（不含值），已在 `.gitignore` 排除 `.env`。

### 4.2 Dockerfile（多階段：build 前端 → node 服務）
```dockerfile
# syntax=docker/dockerfile:1

# ── 1) build 前端 ───────────────────────────────
FROM node:20-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build            # → /app/dist

# ── 2) 安裝正式相依（含後端；better-sqlite3 需編譯）──
FROM node:20-alpine AS deps
WORKDIR /app
# better-sqlite3 為原生模組，alpine 需 build 工具
RUN apk add --no-cache python3 make g++
COPY package.json package-lock.json ./
RUN npm ci --omit=dev        # 只裝 production 相依

# ── 3) 執行階段 ─────────────────────────────────
FROM node:20-alpine AS serve
WORKDIR /app
ENV NODE_ENV=production
ENV PORT=8080
ENV COOKIE_SECURE=true
# DB 路徑：Cloud Run 唯一可寫的是 /tmp（暫存！重佈署即失）
ENV DB_PATH=/tmp/app.db

COPY --from=deps  /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY server ./server
COPY package.json ./

EXPOSE 8080
# 非 root 執行
USER node
CMD ["node", "server/index.js"]
```

### 4.3 Express serve 要點（`server/index.js`）
```js
app.set('trust proxy', 1)                          // Cloud Run 代理
app.use(helmet({/* §3.8 */}))
app.use(express.json({ limit: '32kb' }))
app.use(cookieParser())

app.use('/api', apiRouter)                          // 所有後端端點
app.use(express.static('dist', { index: false }))   // 靜態資產

// SPA fallback：非 /api 的 GET 一律回 index.html（交給前端 router）
app.get(/^(?!\/api).*/, (req, res) =>
  res.sendFile(path.join(process.cwd(), 'dist', 'index.html')))

app.listen(process.env.PORT || 8080)
```
- **順序關鍵**：`/api` 要在 static 與 SPA fallback **之前**，否則 API 路徑被 fallback 吃掉。
- fallback 正則 `^(?!\/api).*` 排除 `/api`，避免 API 404 被導向 HTML。

### 4.4 Cloud Run 部署與機密
```bash
gcloud run deploy jiqiao-shiyun \
  --source . --region asia-east1 --allow-unauthenticated \
  --port 8080 --cpu 1 --memory 512Mi \      # bcrypt+sqlite，記憶體較純靜態高
  --min-instances 0 --max-instances 1 \      # ⚠ SQLite 單機：max=1 才不會多實例各持一份 DB
  --set-env-vars COOKIE_SECURE=true,ALLOWED_ORIGIN=https://<你的網址>,APP_BASE_URL=https://<你的網址> \
  --set-secrets SESSION_SECRET=session-secret:latest   # 用 Secret Manager 注入機密
```
- **機密**：`SESSION_SECRET` 等用 **Secret Manager**（`--set-secrets`），不要用明文 `--set-env-vars`。
- **`--max-instances 1`**：本規格用 SQLite 單機檔案，**必須限制單實例**，否則水平擴充時各實例持有各自 `/tmp/app.db`，session 不共享、登入態亂跳。
- **`--min-instances 0`** 會冷啟動且 `/tmp` 清空 → 資料全失。若要 demo 期間資料短暫存活，設 `--min-instances 1`（仍會在重佈署時重置）。
