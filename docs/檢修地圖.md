# 檢修地圖 — 每個檔案的每個部分在做什麼

> **這份文件的用途**：要改東西時**先查這裡**，直接跳到那個檔案的那一段，
> 不必把整個 codebase 掃一遍（全站 34,704 行）。
>
> **這份文件不取代 `CLAUDE.md`**。兩者分工：
> - **本檔＝「東西在哪裡」**（座標）
> - **`CLAUDE.md`＝「改的時候會踩到什麼」**（雷區）
>
> 動手前的順序：**本檔找位置 → `CLAUDE.md` 搜同一個關鍵字看有沒有雷 → 改 → 回來更新本檔**。

---

## 〇、怎麼用（先讀這 5 行）

1. **用「錨點」找，不要用行號找**。行號會隨著每次改動漂移，本檔的行號一律是 `約 N` 僅供估算；
   **可靠的是錨點**——函式名、CSS 選擇器前綴、路由字串。一律 `grep` 錨點。
2. **改完就回來改這份**。新增畫面／新增 API／新增 CSS 前綴／搬動檔案，都要更新對應那一列。
3. **`npm run build` 會驗這份文件**（`scripts/check-map.mjs`）：本檔提到的檔案、畫面代號、
   CSS 前綴、API 路由若在程式裡找不到，**建置直接失敗**。這是刻意的——
   一份過期的地圖會把人帶到錯的地方，比沒有地圖更糟。
4. 標記說明：`*` ＝ 有 export；`約 N` ＝ 大約在第 N 行；`⚠️` ＝ 這一段 `CLAUDE.md` 有記雷區。
5. 找不到想改的東西時，最後手段是 `grep -rn "畫面上看到的那句文案" src/`——
   本站的文案幾乎都是硬編在 JSX 裡的中文字串，這招幾乎一定找得到。

## 十一、維護規則（這份文件怎麼不爛掉）

**`npm run build` 會跑 `scripts/check-map.mjs`**，驗四件事：

1. 本檔提到的**每個檔案路徑**都存在
2. 〈二〉的**每個畫面代號**都在 `SCREEN_PATH` 裡，而且網址一致
3. 〈三〉的**每個 CSS 前綴**在 `styles.css` 裡真的有規則
4. 〈四〉的**每支 API 路由**在 `server/index.js` 裡真的有註冊

⚠️ 它**不驗行號**——行號本來就會漂，驗了只會逼人為了過閘門去改一堆無意義的數字。
行號是估算值，錨點才是契約。

**改動之後要回來更新哪一段**：

| 你改了什麼 | 回來更新 |
| --- | --- |
| 新增／刪除畫面 | 〈二〉那一列（三表本身另有 `check-nav` 擋） |
| 新增／刪除 API | 〈四〉對應分區 |
| 新增一組 CSS 前綴（`.xx-`） | 〈三〉前綴表 |
| 搬動或改名檔案 | 所有提到它的地方（閘門會抓出來） |
| 在 `nav.jsx` 加全域狀態 | 〈五〉分區表 |
| 加新的建置閘門 | 〈十〉閘門表 |

**踩到雷區時**：把「怎麼避開」寫進 `CLAUDE.md`（那是雷區的家），
本檔只寫「在哪裡」並標一個 ⚠️ 指過去。兩邊寫同一件事會分岔。
